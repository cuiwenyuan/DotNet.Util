## Msg 多语言层性能实测（用户提问「Msg.cs 会不会有性能问题」）

### 结论：**无实际性能问题**，单次开销在消息输出场景可忽略。

### 实测方法
临时在 `Tests/Message/MsgPerformanceTests.cs` 写基准（Stopwatch，100 万次/项，
`[Collection(MsgTestCollection.Name)]` 隔离），Debug + Release 各跑一次，**跑完已删除**，
测试数基线仍为 1202。

### 数据（Release / net8.0，含委托调用开销约 6.7ns，绝对值系统性偏高约 30-50ns）
| 场景 | ns/次 |
|---|---|
| 常量字符串返回（改造前基线） | 6.7 |
| Dictionary OrdinalIgnoreCase 裸查（对照） | 54.1 |
| **Msg.Get 命中 zh-CN** | **92.6** |
| **Msg.Get 命中 en** | **64.0** |
| Msg.Get 缺失键（全链路回退） | 158 |
| Msg.Format 带 1 参数 | 410 |
| EnumUtil.ToDescription（已登记/未登记） | 2145 / 2129 |
| Msg.Clear() + 重装 2×406 词条 | 331 µs/次 |

### 关键判读
1. **Msg 相对裸字典的增量 ≈ 30~40ns**，相对编译期常量的增量 ≈ 85ns。
   对比一次 DB 查询 ~1ms（百万 ns）、一次异常抛出 ~5-50µs → 占比 < 0.1%，**无感**。
2. **`EnumUtil.ToDescription` 2.1µs 是既有反射成本**（`GetType` + `ToString` +
   `GetCustomAttributes`），Msg 只占 2-4%，**不是多语言引入的**。这是全库唯一真正的热点，
   但属历史遗留，与本次改造无关。
3. **全部 319 处 Msg 调用点已逐一定位，无一落在热循环**：
   - 异常抛出（ExpressionEvaluator 7 / Utils 3 / Qqwry 2 / TableInfo 1）
   - 分支赋值（`errorMessage`/`statusMessage`/`result =`，只在失败分支执行）
   - 日志（DisposeBase / SaveEntityChangeLog，仅异常时）
   - `RmbUtil` 2 处只在溢出/非数字的错误返回分支。**无热路径。**

### 已识别的 3 个可优化项（尚未改动，等用户确认）
1. 🟡 `Msg._initialized` 非 volatile —— 内存可见性隐患（正确性 > 性能），建议加 `volatile`。
2. 🟡 内层 pack 用 `StringComparer.OrdinalIgnoreCase` —— 键是生成的精确常量，
   改 `Ordinal` 可省 hash 开销并消除 `msg0001`/`Msg0001` 歧义；外层 culture 字典保留
   OrdinalIgnoreCase（用户可能传 `en-us`）。
3. 🟡 `BaseResult.StatusMessage = Msg.Get(...)` 是**实例字段初始化器** → 每次 `new BaseResult()`
   都查一次字典（~90ns）。批量建对象时有轻微放大；但改成属性会破坏二进制兼容（用户明确要求保），
   改 `static` 缓存则语言切换后失效 → **建议不动**。

## 性能优化两项落地（volatile + Ordinal）—— 用户拍板「把前两项落掉」

### 改动（`src/DotNet.Util/Message/Msg.cs`）
1. **`private static volatile bool _initialized;`**
   `EnsureInitialized()` 的快路径在 `lock` 之外读该字段，非 volatile 存在内存可见性隐患
   （线程 A 完成初始化后线程 B 可能仍读到 false）。加 `volatile` 零风险。
   ⚠️ **同类隐患未动**：`private static string _language` 也是锁外读写的静态字段
   （`CurrentLanguage` 的 get/set），有同样问题，本轮按「严格增量」未改，待用户决定。
2. **`RegisterCore` 内层 pack：`StringComparer.OrdinalIgnoreCase` → `StringComparer.Ordinal`**
   键由代码生成、调用点也是精确字面量，无需忽略大小写。
   **行为变化：消息键从此区分大小写**（`Msg.Get("msg0001")` 不再命中 `Msg0001`，
   会回退返回键本身）。外层 `Packs`（culture 字典）**保留** OrdinalIgnoreCase，
   仍容忍 `"en-us"` / `"ZH-cn"` 写法。
   事前已 grep 全库确认无调用点依赖大小写不敏感。
3. XML 注释同步：`Get` / `Register` / `LoadJsonOverride` 三处补「键区分大小写」说明。
